## What it is for, and when to run it

Use it to set up the archive sink, and when one of these fires: `AledgentCoreArchiveLag` (page),
`AledgentCoreArchiveStale` (page), `AledgentCoreArchiveConflict` (page, security) or
`AledgentCoreCheckpointLate` (warning). Suggested owner: platform.

In this release the book's writer is one core Agent on one execution node (`DEC-22`). The archive is what
bounds the loss of that node's storage until the runtime supports membership change.

- **What streams.** `aledgent-core-host serve --archive <spec>` ships every decision's bytes of `archive.bin`
  (every committed input, hash-chained) and `replies.jsonl` (every reply) to the archive, at most
  `--archive-interval-ms` (default 1 s) after the decision. A checkpoint of `agent.state` (the Agent's
  runtime state) follows every `--checkpoint-every` inputs (default 50 000) or 15 minutes.
- **Never on the critical path.** Nothing the core answers waits for the archive. A slow or absent sink only
  grows the lag, and the lag pages.
- **Not shipped:** the replica's leaf store. It is a projection of `archive.bin`, which a restore rebuilds
  and checks root by root.
- **The sink** is an S3-compatible object store with **Object Lock** (compliance mode) and server-side
  **KMS** encryption on every object, or a directory for tests and the drill. A writer refuses to start on S3
  without both.

```text
--archive 's3://<bucket>/<prefix>?region=<region>&kms-key-id=<archive key id>'
--archive fs:<directory>
```

Every object is locked in compliance mode for **400 days** by default; the spec's `lock-mode` and
`retain-days` override that, and only together. Credentials come from the instance role or the environment,
never an argument.

### The recovery point

| What is lost | What is lost with it |
|---|---|
| The core's node and its volume, ingress's database intact | **Nothing acknowledged.** The archive restores to its last segment, and `opsctl restore core-tail` re-decides the window after it from the received-log. Each reply must match the one recorded |
| The core's node, and ingress's received-log with it | The decisions committed after the archive's last segment: the archive's lag at the failure. About 1 s plus one upload while the sink is healthy; `AledgentCoreArchiveLag` pages at 5 minutes. By design the archive stays asynchronous and no decision waits for the sink |
| The archive's newest segments (a damaged archive) | The restore refuses. `--accept-damaged-archive` restores to the point before the damage, and the received-log's tail must cover the rest |

`NFR-21` (c) asks that losing one node's storage loses nothing acknowledged. The single voter meets that
only while the received-log survives. The archive bounds the double loss and does not close it; a replicated
core does (`F-021`).

## Preconditions (setting it up)

You provision the sink; nothing here creates it.

- **A bucket** of your naming. Object Lock is enabled at creation, with default retention COMPLIANCE, 400
  days. Versioning is on, and **no** lifecycle rule expires current versions.
- **A KMS key** used only for the bucket's encryption. The core host's role may generate data keys and
  decrypt; the restore role may decrypt only.
- **The core host's role** may put objects, put object retention, get objects and list the bucket under the
  core's prefix. It never gets delete or bypass-retention permissions.
- **The restore role** (the drill's isolated host, total-loss recovery) may get objects, get object retention
  and list the bucket, and nothing else.
- **The exporter** has `[records] core_archive` pointing at `<state>/archive.status.json`. The core's backup
  age is then the archive's (`aledgent_backup_last_age_ms{store="core"}`).
- `opsctl archive verify --from <spec> --config <deployment config> --anchors-rpc <archive node URL>`
  passes (use `--no-anchors` only where no archive node exists yet; the anchor checks are then not run).

## Steps, by alert

### `AledgentCoreArchiveLag`

Decisions have waited more than 5 minutes for the sink. Losing the node now loses them unless ingress's
received-log survives.

1. Read the status: `opsctl archive status --state <state dir>`. Check `failures`, `last_error` and
   `pending_bytes`.
2. `Unavailable` from the object store means the network path, the role or the KMS key. Fix the cause. The
   archiver retries with backoff, up to 30 s apart, and catches up by itself; a backlog over 16 MiB goes up in
   parts.
3. Do not restart the core host to unstick it. A restart is safe (the archiver resumes where the sink
   stands) but it fixes nothing the sink refuses.

### `AledgentCoreArchiveStale`

The archiver has not written its status for 2 minutes. Either the core host is down ([The core stalls or
halts](../core-halt/), [Replace a node](../replace-node/)) or the exporter cannot read the file.

### `AledgentCoreArchiveConflict`

The core host refuses to write because the archive's history is not its logs'. Either two hosts run one core
identity (`INV-25`), or a node was brought up from an older copy (a snapshot) while the archive went further.

1. **Do not delete anything in the bucket.** Object Lock forbids it anyway, and the archive is the record.
2. Find the second writer and fence it. If the node was restored from a snapshot, the archive is the newer
   copy: restore from it ([Total-loss recovery](../total-loss-recovery/), path B) instead.
3. Escalate to the owner if the archive and a live node disagree on a decision both answered. That is a
   divergence ([Divergence](../divergence/)).

### `AledgentCoreCheckpointLate`

No checkpoint for 2 hours while inputs commit. Nothing is lost; a restore re-sends every input since the last
checkpoint through the Agent, which takes longer. Check `last_error` in the status.

## Verify

- `opsctl archive status` shows no recent failures and `pending_bytes` near zero; the lag alert clears.
- `opsctl archive verify` passes against the archive.
- The restore drill passes ([The restore drill](../restore-drill/)).

## Roll back

Nothing here changes the book. A sink configuration is reverted by restarting the core host with the
previous `--archive` spec; a new prefix starts a new history, which a restore must then be given
([Total-loss recovery](../total-loss-recovery/)). Nothing in the bucket is ever removed (`REQ-AT-3`).
