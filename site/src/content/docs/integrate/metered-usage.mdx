Cites `INV-14`, `REQ-OP-2`, `US-C2`, `REQ-BA-4`, `REQ-OP-10`, `REQ-CS-3`.

A reservation holds value against an account at once (`REQ-BA-4`). It ends in exactly one of two ways:
**capture**, which moves value from the reservation to a destination, or **release**, which gives all of
it back. A reservation and its capture or release are one object, matched by identity (`INV-14`): what is
reserved comes from the book, never from the caller. **A capture may clear less than the reservation**: the
difference returns to the payer's available balance in the same posting (`REQ-OP-2`, `US-C2`). A capture
above the reserved amount is `ERR-AmountMismatch`, and nothing changes. A reservation is captured or
released once.

Every integrator that charges for usage meets this. Pick the pattern by when you know the cost.

## The cost is known before the work

Reserve the cost, do the work, then capture or release. Use your task id in the reservation's client key.

```sh
# 1. Reserve. Acknowledged at Received (202); the decision follows.
curl -X POST "$INGRESS/v1/reservations" -H "Authorization: Bearer $API_KEY" \
  -H "client-key: task-7f3c2a-reserve" -H "content-type: application/json" \
  -d '{"payer":"'$USER_ACCOUNT'","asset":"CRD","amount":"1500","reference":{"task":"7f3c2a"}}'

# 2. Wait for Reserved (notification, or GET /v1/operations/{reference}). Rejected means declined.

# 3a. The work succeeded: capture all of it into your collection account.
curl -X POST "$INGRESS/v1/reservations/$RESERVATION/capture" -H "Authorization: Bearer $API_KEY" \
  -H "client-key: task-7f3c2a-capture" -H "content-type: application/json" \
  -d '{"destination":"'$COLLECTION_ACCOUNT'","cleared":"1500"}'

# 3b. The work failed: release it.
curl -X POST "$INGRESS/v1/reservations/$RESERVATION/release" -H "Authorization: Bearer $API_KEY" \
  -H "client-key: task-7f3c2a-release" -H "content-type: application/json" -d '{}'
```

If the cost falls before the capture, capture the lower amount: the rest returns to the user at once. If it
rises above what you reserved, capture what you reserved and charge the rest with a `transfer` (below), or
release and reserve again for the new amount.

## The cost is known only afterwards

An LLM proxy, say: the price depends on the tokens the call used. Reserve a **cap** before the call, then:

- **The cost is at or below the cap:** `capture` the real cost, as `cleared`. The rest of the cap returns
  to the user's available balance in the same posting. Done.
- **The cost exceeds the cap:** `capture` the whole cap, then charge the excess with a `transfer` from the
  user's account to your collection account, with the request id in its client key
  (`request-<id>-excess`). A capture above the reservation is refused.

For the second case the grant over the user's account needs `transfer` as well as `reserve`, `capture` and
`release`. Limit it to your collection account with `counterparties`.

<Aside type="caution" title="Trade-off, stated plainly">
Only the cap is held. If the cost exceeds it and the user spends the rest of their balance elsewhere first,
the excess transfer is refused (`ERR-InsufficientAvailable`) and you have done that part of the work
unpaid. Size the cap so the cost rarely exceeds it.
</Aside>

## At volume

One reservation per call is many operations. For a session of many calls:

- reserve one **budget** for the session;
- meter the calls on your side;
- at the session's end, capture the session's total from the budget (the rest returns to the user), or
  release the budget if nothing was used.

If the total exceeds the budget, the same trade-off applies to the transfer for the excess.

## Keys for each step

Each step is its own command and needs its own client key, stable across retries: derive them from your
own ids (`task-<id>-reserve`, `task-<id>-capture`), never from a timestamp. A retry with the same key
returns the first reply; a different request under a used key is `ERR-ClientKeyReused` (`REQ-OP-10`).
